База ссылок: https://github.com/Openwrt-Passwall/openwrt-passwall/tree/409d28cc7d7d2d806039bf03f7ebf4724c03ea99/luci-app-passwall . Пути ниже относительно этой директории.

## 1. UI → переменные запуска
- luasrc/model/cbi/passwall/client/other.lua:125–151: при доступности модулей форма предлагает TCP REDIRECT/TPROXY; IPv6 TProxy — отдельный флаг, default=0, с experimental-предупреждением. При IPv6 TProxy форма предлагает только TCP TPROXY. Это ограничение формы, не доказательство принудительной нормализации любого импортированного UCI.
- root/usr/share/passwall/app.sh:1838–1881: TCP_PROXY_WAY читается с fallback redirect, PROXY_IPV6 — из ipv6_tproxy с fallback 0. FILTER_PROXY_IPV6 отдельно читается из filter_proxy_ipv6 с fallback 0. Следовательно, выключение IPv6 TProxy само по себе не включает DNS-фильтрацию IPv6.
- Там же: CLIENT_PROXY и LOCALHOST_PROXY раздельны, оба с fallback 1. Уже выбранное исключение обычного трафика Ubuntu (D-057) отличается от fallback localhost_proxy референса, но соответствует наличию отдельного управления этой областью.

## 2. Firewall → policy routing → Xray
Ветка nftables, root/usr/share/passwall/nftables.sh:
- :46: FWMARK=0x50535731. :138–145: TPROXY/TPROXY6 сопоставляют уже установленную метку и направляют пакет на локальный порт (для IPv6 `tproxy ip6 to :port`).
- :162–166: отдельные prerouting hooks для NAT и mangle. Это не один лишь default route на машину: перехват требует правил firewall и принимающего transparent listener.
- :1226–1227: IPv4 policy rule по метке, таблица 999, local route через lo.
- :1230–1245: IPv6-цепочки исключают LAN6, VPS6, reply direction; OUTPUT также учитывает block/direct sets и пропускает mark с младшим байтом 0xff.
- :1265–1273: только при PROXY_IPV6=1 подключаются IPv6 prerouting/output chains, исключается WAN6, добавляются `ip -6 rule ... table 999 priority 999` и `ip -6 route add local ::/0 dev lo table 999`.
- Это не равнозначно запрету всех IPv6-пакетов при выключенном флаге. Вывод ограничен этой веткой: IPv6 TProxy jump и policy route не включаются. Остальные firewall/DNS-правила нужно учитывать отдельно.

Генератор luasrc/passwall/util_xray.lua:1649–1687:
- В ЭТОМ snapshot inbound называется `tunnel`, а не автоматически предполагаемый по старым версиям `dokodemo-door`.
- followRedirect=true; отдельные tcp_redir/udp_redir на redir_port. TCP получает выбранный tcp_proxy_way; UDP сохраняет tproxy.
- Sniffing включается условно: override_dest либо shunt; HTTP/TLS/QUIC, routeOnly и FakeDNS зависят от параметров. Нельзя считать распознавание домена включенным/надежным для любого потока.
- :166–169 обычный outbound sockopt содержит mark=255, что связано с исключением 0xff в OUTPUT. Это не та же метка, что FWMARK для доставки inbound.

## 3. DNS-фильтр IPv6 — другая функция
- luasrc/model/cbi/passwall/client/global.lua:222–223 и acl_config.lua:332–333: отдельный filter_proxy_ipv6, default=0.
- app.sh:1875–1881: direct и remote query strategy изначально UseIP; FILTER_PROXY_IPV6=1 меняет REMOTE_DNS_QUERY_STRATEGY на UseIPv4 и задает DNSMASQ_FILTER_PROXY_IPV6.
- Разные DNS-ветки дополнительно меняют DNSMASQ_FILTER_PROXY_IPV6 (например :657,741,1158,1201). Полная цепочка dnsmasq/chinadns-ng/smartdns/Xray еще не прочитана; нельзя объявлять эти две строки универсальным способом блокировки AAAA.
- Ограничение DNS-ответов само по себе не доказывает отсутствие обхода через literal IPv6, кэш или сторонний DoH. Это граница механизма, не результат сетевого теста.

## 4. Что это означает для Ubuntu с одним NIC
PassWall устанавливает эти правила на самом OpenWrt-роутере. Raylane будет на отдельной машине: доставка пакетов от роутера и обратный путь — дополнительная часть схемы, которой не заменяет копирование скрипта. Сохранение IPv6-переключателя как возможности референса можно оценивать лишь вместе с IPv6-доставкой трафика на Ubuntu; выключение IPv6 на всех устройствах не следует из устройства PassWall.

Технический кандидат для исследования — Linux nftables + policy routing + transparent Xray listener по образцу этой ветки. Это НЕ выбор реализации. Перед переносом нужны анализ конфликтов меток/таблиц, привилегий, исключений upstream, IPv6 next-hop/RA и обратного пути, без переноса UCI/ubus/fw4-зависимостей как зависимостей продукта. Нельзя копировать фиксированные mark/table 999 без проверки окружения.

## 6. DNS → наборы адресов: прослеженная ветка dnsmasq
helper_dnsmasq.lua:460–565 читает direct_host и proxy_host. В обычной dnsmasq-ветке direct-домены получают LOCAL_DNS и наборы psw_white/psw_white6; proxy-домены получают TUN_DNS и psw_black/psw_black6 (либо ACL-specific names). При USE_CHINADNS_NG=1 эта обработка DNS списков пропускается: нельзя переносить вывод на все DNS-backends.

При NO_PROXY_IPV6=1 для proxy-доменов вызывается set_domain_address(domain,"::"), IPv6 black-set не добавляется. Это генерация DNS-конфига, не firewall-запрет IPv6. :730–764 записывает файлы с `address=/.domain/::`, `server=/.domain/resolver` и `nftset=/.domain/sets` (либо ipset). Таким образом, в этой схеме DNS не просто разрешает имя: ответы должны наполнять адресные sets, используемые firewall. Прочитанный генератор доказывает создание директив, не фактическое наполнение на работающем dnsmasq. Поддержка nftset в конкретной сборке, кэш, время жизни записей, shared IP/CDN и обход DNS клиентом требуют отдельных проверок.

nftables.sh:450–475: в прочитанном ACL-блоке DNS TCP/UDP 53 исключается из обычного mangle-перехвата и redirect-ится отдельной цепочкой PSW_DNS. Затем для обычного трафика block-set проверяется перед direct-set; direct выполняет return. Это локальный порядок данного блока, не доказанный глобальный порядок всех ACL/shunt/port-исключений. Перехват порта 53 не является перехватом произвольного DoH/DoT.

## 7. Штатный stop не является fail-closed
app.sh:1704–1760: сначала стартуют процессы/глобальный узел и DNS; при ошибке start_global/start_dns вызывается stop и возвращается ошибка. Firewall start вызывается после этих шагов. Также изменяются настройки OpenWrt dnsmasq и bridge sysctl — это явные платформенные зависимости, не готовый переносимый менеджер Ubuntu.

app.sh:1777–1818: stop сначала вызывает firewall stop, затем завершает процессы, удаляет сгенерированную DNS-конфигурацию и восстанавливает часть настроек dnsmasq/sysctl. nftables.sh:1602–1617 вызывает del_firewall_rule; :1503–1522 удаляет PSW-переходы/цепочки, policy rules и local routes обеих IP-семей. Следовательно, в этой процедуре нет сохраняемого запрета прямого выхода proxy-назначений после остановки. Фактический доступ далее зависит от остального firewall/маршрутов; нельзя утверждать, что stop обязательно блокирует интернет или обязательно открывает его в любой сети.

Отличие от D-055: требование Raylane «не выпускать выбранные proxy-назначения напрямую при недоступности прокси» нельзя обеспечить простым копированием startup-error cleanup/stop из PassWall. Необходим отдельный жизненный цикл защитных правил, включая неудачный запуск/применение; конкретная реализация пока не выбрана.

## 8. Crash процесса отличается от stop
monitor.sh:11–16 проверяет включенные ACL и start_daemon (fallback 0), берет lock, ждет 58 секунд. Далее проверяет PID и время старта записанных процессов и повторно запускает записанную команду; максимум 10 рестартов на запись, счетчики очищаются при смене даты, интервал цикла 58 секунд. Это наблюдение за наличием процесса, не проверка доступности внешнего proxy-сервера или работоспособности DNS. В прочитанном monitor.sh нет вызова firewall stop при обнаружении исчезнувшего процесса. Поэтому нельзя приравнивать crash к штатному удалению правил: результат трафика при оставшихся правилах и отсутствующем listener еще требует теста. Способ подключения монитора к запуску и прочие watchdog-компоненты требуют дальнейшей трассировки.

Нельзя ограничиться переносом формы узлов и JSON Xray: в исследованной ветке есть согласованная работа DNS-генератора, динамических sets, ACL, policy routing и управляющих скриптов. ## 10. ACL, глобальная политика и engine shunt — разные уровни
nftables.sh:247–266 обходит отдельные ACL из TMP_ACL_PATH, затем :609 начинается блок default при ENABLED_DEFAULT_ACL=1 и CLIENT_PROXY=1. В этом блоке :611–636 сначала исключаются no-redir ports, :638–654 настраивается DNS redirect, :657 и далее block предшествует direct. Поэтому фраза «block всегда имеет высший приоритет» была бы неверна: ранее существуют локальные/служебные и портовые исключения. Порядок обхода отдельных ACL здесь определяется перечислением каталогов, а не доказанным порядком UI.

В прочитанном TCP/UDP ACL-фрагменте :545–600 после ранних исключений идут FakeDNS, proxy list, GFW list, CHN action, shunt set, затем общий proxy-mode. Действия зависят от портов/семейства и режима; get_jump_nft(:232–245) для direct проверяет отсутствие FWMARK. PSW_RULE(:1155–1161) восстанавливает packet mark из ct mark, помечает новые TCP SYN/UDP и сохраняет mark обратно. ВАЖНО: выражение `meta mark ${FWMARK}` в TPROXY helper(:138–145) — условие совпадения метки, а не ее установка; прежняя формулировка раздела 2 «ставят эту метку» исправляется: helper доставляет уже помеченный пакет. Установка выполняется PSW_RULE/PSW_DIVERT. Поэтому финальный TPROXY helper после списка не равен безусловному захвату всех оставшихся пакетов.

Xray shunt — дополнительный уровень: util_xray.lua:1414–1455 определяет _direct/_blackhole/_default/конкретный узел и default_node с fallback _direct. :1500–1600 формирует правила из source/network/port/protocol, отдельно доменное и IP-правило; доменные значения также сохраняются в dns_domain_rules. Строки rule-set:/rs:/ext: в прочитанной ветке пропускаются, поэтому имя «готовые наборы» не доказывает поддержку любого формата. :1635–1645 добавляет завершающее правило default для tcp,udp. Реальный порядок сопоставления требует учета всех ранее созданных routing rules, а не только финального default.

## 11. Другие DNS-генераторы: ограниченная дополнительная проверка
helper_chinadns_add.lua:114–116 генерирует china-dns/trust-dns и отдельно filter-qtype 65; :343–345 — group-ipset и условный no-ipv6 tag:proxylist; :367 аналогичный no-ipv6 tag:gfw. helper_smartdns_add.lua:534–578 генерирует domain-set/domain-rules с nameserver proxy, -no-cache и nftset/ipset; при NO_PROXY_IPV6=1 использует -address #6 и IPv4 set, иначе -address -6 и обе семьи. Это подтверждает разные реализации одной UI-возможности, но не полную эквивалентность backends или проверку их бинарников. Не объявлять весь chinadns/smartdns исследованным по этим фрагментам.

## 12. Отдельная Ubuntu: вынесен анализ топологии
UBUNTU_NETWORK_PORTABILITY.md отделяет факты PassWall от технических гипотез переноса. Ключевой риск: повторное направление возвращаемого direct-трафика на Ubuntu, если правило роутера ориентируется только на исходный IP клиента. Метки Linux не переносятся между машинами. Разобраны forwarding, direct outbound Xray и возможные способы различения путей без выбора или применения одного из них. Требования к отказу и DNS нельзя подтвердить без этого анализа.

## 13. Проверка окружения и подключение монитора
app.sh:21–75 выбирает nftables не просто по наличию Linux nft: требуются dnsmasq с nftset и команда fw4. Альтернатива — iptables+ipset+dnsmasq ipset. Далее проверяются пакеты через opkg/apk-пути; для nft ветки выставляется nftflag=1, dnsmasq <2.92 вызывает рекомендацию обновления. При отсутствии подходящей среды здесь выводится предупреждение, а не доказанный fail-closed barrier. Ubuntu-перенос должен проверять Linux capabilities и сборку DNS отдельно, а не устанавливать fw4 ради прохождения OpenWrt-ветки.

app.sh:945–953 подключает monitor.sh через start_crontab только при активных ACL и start_daemon=1; это закрывает вопрос подключения монитора из раздела 8. Значение fallback=0. Отсутствие мониторинга не эквивалентно остановке firewall; монитор сам по себе не обеспечивает D-055.
