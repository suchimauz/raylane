# Перенос сетевого пути PassWall на отдельную Ubuntu

UNDER_RESEARCH / NOT APPROVED. Документ выводит ограничения из выбранной топологии и трассировки PASSWALL_NETWORK_TRACE.md; это не инструкция для выполнения и не испытанная конфигурация. Никакие адреса частного стенда не используются.

## Подтвержденные исходные условия
OpenWrt остается основным роутером; Ubuntu находится в LAN с одним NIC. Интернет-трафик всей LAN направляется через Ubuntu вручную настроенным роутером (D-052). Direct по умолчанию, выбранные назначения через proxy; при недоступности proxy прямой обход запрещен (D-053–055). Полный отказ Ubuntu допускает ручное восстановление (D-056). Обычный локальный трафик Ubuntu не перехватывается (D-057). Решение о клиентском IPv6 не принято, карточка отменена.

## Где референс и где дополнительная задача
PassWall работает на роутере, который уже видит LAN→WAN. Его nftables выполняет адресные/портовые исключения, маркировку, доставку локальному Xray и DNS redirect. На отдельной Ubuntu эти же Linux-механизмы не заставляют роутер доставить ей пакеты. OpenWrt должен направлять нужный транзит на Ubuntu, но не отправлять туда повторно возвращаемый direct-трафик и соединения движка.

## Три пути пакетов (логическая схема, не готовые маршруты)
1. **Direct через forwarding**: клиент → OpenWrt → Ubuntu → OpenWrt → WAN. Ubuntu сохраняет адрес клиента, если не применяется SNAT. Если правило OpenWrt выбирает пакет только по этому адресу, возврат с Ubuntu может опять попасть под правило: петля. Локальная skb/conntrack-метка Ubuntu не передается как такая же метка на другую машину.
2. **Proxy через Xray**: клиент → OpenWrt → Ubuntu TPROXY/REDIRECT → локальный Xray → отдельное соединение к внешнему узлу через OpenWrt. Исходящие соединения движка должны быть исключены из повторного направления на Ubuntu на роутере, а также из локального перехвата. Ответ клиенту формируется прозрачным listener; route/source/conntrack необходимо проверить отдельно.
3. **Direct через outbound Xray**: весь выбранный TCP/UDP доставляется в Xray; engine routing выбирает direct или proxy. Соединение к назначению инициируется движком, а не обычным forwarding пакета клиента. Это может упростить различение на роутере, но связывает direct-доступ с живым Xray и меняет производительность/поддерживаемые протоколы. Вариант не выбран; наличие такого outbound в референсе не означает, что PassWall всегда отправляет через него весь direct-трафик.

## Кандидаты решения проблемы возвращаемого direct-трафика
- Различать первый/повторный проход на роутере по проверенному признаку пути (L2/interface/conntrack в подходящей схеме). При одном общем LAN нельзя обещать, что простого ingress-interface достаточно. Нужны точные hook и условия.
- SNAT на Ubuntu для транзита: роутер видит адрес Ubuntu и может исключать его. Цена — изменение видимости исходного клиента, дополнительный conntrack/NAT и особенности обратного пути. Не выбран, не применять автоматически.
- Логическое разделение путей, например VLAN при поддержке оборудования: один физический NIC не исключает несколько логических интерфейсов, но меняется ручная схема сети. Не утверждено.
- Direct через Xray, описанный выше: отдельный компромисс, не незаметная замена Linux forwarding.

Ни один кандидат не объявлен работающим без проверки. Не предлагать пользователю выбирать эти механизмы до технического сравнения.

## DNS и локальный доступ
Запрос клиента к LAN-адресу роутера обычно завершается на самом роутере, не является WAN-forwarding и не попадет на Ubuntu от одной политики интернет-трафика. Поэтому нужно отдельно связать клиентский DNS и резолвер, который наполняет адресные sets. Возможны ручная настройка DNS выдачи клиентам или явный forwarding DNS с роутера; конкретный вариант не выбран. Локальный доступ к панели/роутеру должен оставаться вне общего перехвата, включая сценарий восстановления. Нельзя объявлять DoH клиента обслуженным только правилом TCP/UDP 53.

## IPv6
Сохраняем факт референса: отдельный IPv6 TProxy и независимый DNS-фильтр. Для Ubuntu требуется IPv6-доставка клиентского трафика и обратный путь; IPv4 policy route не покрывает IPv6. RA/default route клиентов и link-local next-hop влияют на путь. Нельзя автоматически рекомендовать NAT66 или отключение IPv6 как «то же, что PassWall».

## Отказ и применение
Копирование stop PassWall не обеспечивает D-055: правила перехвата удаляются. Нужны отдельно определенные состояния: отсутствует внешний узел, умер Xray, DNS недоступен, кандидат конфигурации не запустился, штатная остановка и полный отказ Ubuntu. Защита proxy-назначений должна учитывать готовность DNS/sets: пустой набор после запуска не должен незаметно превращать требуемую блокировку в direct. Конкретная политика boot/readiness и намеренной остановки еще не утверждена.

## Матрица будущих проверок — не запускать сейчас
- Повторный проход клиента через OpenWrt, отсутствие петли и корректная conntrack-запись.
- Direct TCP/UDP, ответы и асимметрия пути на одном LAN; источник пакетов, rp_filter и ICMP redirects.
- Transparent TCP/UDP и исключение upstream-узлов; перенос исходного назначения.
- DNS → IPv4/IPv6 sets, TTL/cache, совпадающие IP разных доменов, клиентский DoH и literal IP.
- Отказ Xray/upstream/DNS, пустые sets при старте, сохранение прямого доступа для direct-направлений без выпуска proxy-направлений.
- Доступ к управлению после отключения Ubuntu; ручное восстановление с явным изменением гарантий.

Следующий технический шаг: завершить статическое сопоставление глобальных/ACL/shunt правил и lifecycle; затем оформить сравнение кандидатов с конкретными проверяемыми условиями, не переходя к установке или настройке сети. Статус всех сетевых проверок: NOT_RUN.
