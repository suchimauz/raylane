## User Scenarios & Testing
Все сценарии ниже PROPOSED; результаты тестов NOT_RUN. Это критерии для обсуждения, не заявление о готовой реализации.

### US-01 — Настроить выбранный внешний узел (приоритет OPEN_QUESTION)
Пользователь задает подключение VLESS, SOCKS, HTTP или WireGuard без настройки OpenWrt со стороны приложения.
- Given выбранный протокол и согласованная версия движка, When пользователь сохраняет допустимые поля, Then значения сохраняют согласованную семантику и преобразуются в ожидаемую конфигурацию.
- Given невыбранный транспорт или неизвестная опция, When она приходит из ввода/импорта, Then приложение не заменяет ее молча другим режимом; конкретная политика отклонения/сохранения требует решения.
- Независимая проверка: синтетические конфигурации и сравнение нормализованных полей с референсом; без реальных секретов.

### US-02 — Понять ошибку до применения (приоритет OPEN_QUESTION)
- Given REALITY+WebSocket либо REALITY+HTTPUpgrade и исследованная версия Xray, When конфигурация проверяется, Then несовместимость выявляется, а не показывается успешное подключение.
- Given недопустимый порт, ID, reserved либо JSON, When выполняется проверка, Then ошибка указывает поле и причину. Ужесточение относительно PassWall обсуждается отдельно.
- Given проверка не запускалась, Then статус NOT_RUN, а не PASS.

### US-03 — Управлять сложными настройками понятно (приоритет OPEN_QUESTION)
- Given выбранный режим, When пользователь редактирует настройки, Then зависимости объяснены и отличены от ограничений движка.
- Given сокращение движения включено, Then переходы не требуют анимации для понимания состояния.
- Given сохраненные и примененные настройки различаются, Then интерфейс не выдает сохранение за успешное применение. Этот UX-процесс пока PROPOSED.

## Requirements
### CONFIRMED
- FR-001: приложение самостоятельно работает на Ubuntu и не зависит от OpenWrt API/LuCI/SSH.
- FR-002: выбранные подключения — VLESS, SOCKS, HTTP-прокси, WireGuard. Локальные inbound-сервисы и системный WireGuard этим не утверждены.
- FR-003: семантика выбранных полей сохраняется максимально точно; отклонения обсуждаются.
- FR-004: Xray-core — основной кандидат; второй движок сейчас не реализуется.
- FR-005: UI следует Apple Design Skill, без копирования LuCI.

### PROPOSED / NEEDS CLARIFICATION
- FR-P01: доменная модель узла отделена от JSON конкретной версии Xray; отсутствующее, пустое и явное default различаются там, где это меняет поведение.
- FR-P02: сохраненная конфигурация проверяется движком до применения; применение/откат и права доступа еще проектируются.
- FR-P03: секреты маскируются в UI и диагностике; формат хранения и выдачи прав не выбран.
- FR-P04: неподдерживаемые сочетания не исправляются автоматически. Решить политику для исторических/импортированных полей.
- FR-P05: каждому принятому полю сопоставлены UI default, нормализация, engine default, validator, зависимости, JSON path и тестовые примеры.

### Key Entities — PROPOSED
Connection: выбранный протокол, общие метаданные, адрес/порт, учетные данные, параметры транспорта/защиты, дополнительные параметры.
EngineCapabilityProfile: версия движка и подтвержденные допустимые комбинации.
ValidationReport: ошибки, предупреждения, NOT_RUN/PASS/FAIL, версия и доказательства выполнения.
Ни SQL-схема, ни язык реализации этим не выбраны.

## Edge Cases
- Поле скрыто, но значение осталось после импорта или переключения режима.
- flow задан, но TLS выключен и encryption=none; PassWall его не передает.
- Пароль без имени пользователя HTTP/SOCKS: исследованный Xray не создает учетную запись.
- Отсутствующий/пустой путь и domain_strategy; Lua трактует их по-разному.
- XHTTP Extra содержит весь объект либо только extra, пользовательский User-Agent уже присутствует.
- FinalMask заменяет автоматически сформированные настройки, а не объединяет их.
- WireGuard endpoint IPv6, reserved 0/3/иная длина, отрицательные/нечисловые keepAlive и MTU.
- DNS адреса узла требует DNS-запроса через еще не работающий узел; bootstrap-петля.
- Неверный gRPC timeout; устаревший импорт transport=quic; REALITY+недопустимый transport.
- Переключение/удаление узла, на который ссылается цепочка: политика не определена.

- SC-005: нет незаявленной OpenWrt-зависимости; UI и конфигурация не теряют выбранные расширенные поля.

## Clarifications
- CONFIRMED D-009: сохранить все шесть транспортов VLESS: RAW (TCP), WebSocket, gRPC, HTTPUpgrade, XHTTP, mKCP. Вопрос о наборе транспортов закрыт. Security/flow и дополнительные возможности не утверждены этим выбором. Ранее перечисленный вопрос о выборе транспортов считать уточненным этой записью.
- CONFIRMED D-010: в первой версии VLESS допускается только с TLS или REALITY. Режим без них запрещен; это явное согласованное отклонение от PassWall. Нельзя автоматически включать незащищенный режим ради поддержки транспорта. Все шесть транспортов остаются целью, их совместимость с защитой проверяется отдельно; конфликт выносится на согласование.
- Acceptance criterion (следствие D-010): конфигурация VLESS без TLS/REALITY не должна считаться допустимой для применения. UI-default и обработка импортированного узла требуют уточнения; автоматическое добавление TLS не разрешено.
- CONFIRMED D-011: поддержать все три значения flow: пустое, xtls-rprx-vision, xtls-rprx-vision-udp443; без автоматической подмены. Пустой flow не означает отключение TLS/REALITY.
- Acceptance criterion (D-011): все три значения сохраняются без потери; генерация учитывает согласованные ограничения engine. Для обычного Vision и Vision-udp443 проверяется различие обработки UDP/443, не обещается доступность UDP вне движка.
- CONFIRMED D-012: несовместимые настройки разрешено сохранять как невалидный черновик с понятной ошибкой, но запрещено применять; без автоматической подмены транспорта/flow/security. Это уточняет FR-P04 и US-02.
- Acceptance criterion (D-012): при сохранении REALITY+WebSocket/HTTPUpgrade для отвергающей сочетание версии Xray узел остается доступным для исправления, помечен невалидным, причина видна, применение блокируется. Значения не исправляются молча. До проверки нельзя утверждать валидность. Жизненный цикл уже примененной конфигурации пока OPEN_QUESTION.
- CONFIRMED D-013: «Сохранить» и «Применить» — отдельные действия. Сохранение не влияет на работающую конфигурацию; изменение работы требует явного применения проверенного состояния. Это уточняет US-03 и FR-P02 в части разделения действий, но не утверждает механизм отката.
- Acceptance criterion (D-013): изменение и сохранение валидного либо невалидного узла не изменяет активную конфигурацию и не инициирует ее перезапуск. Применение возможно только отдельным действием после проверки; UI различает сохраненное и примененное состояние. Гарантии сохранения соединений при самом применении не определены.
- CONFIRMED D-014: сохранить для VLESS редакторы XHTTP Extra и FinalMask. Проверять JSON и совместимость движка, объяснять назначение; FinalMask заменяет автоматически сформированный объект целиком, не выполняет merge. Решение не распространяется автоматически на WireGuard и другие протоколы.
- Acceptance criterion (D-014): валидный XHTTP Extra нормализуется согласно описанному референсу; собственный FinalMask заменяет автоматически собранный, а не смешивается с ним. Ошибка JSON или несовместимость исключает применение. Синтаксически валидный JSON сам по себе не означает совместимость с Xray. Разрешение сохранять синтаксически невалидный JSON как текстовый черновик еще требует уточнения.
- CONFIRMED D-015: XHTTP Extra/FinalMask сохраняются только при синтаксически корректном JSON. Ошибка синтаксиса блокирует сохранение; текст остается в редакторе для исправления, но его долговременная сохранность не гарантируется. Это исключение к широкому прочтению D-012: корректный JSON с несовместимой семантикой можно сохранить невалидным черновиком, применять нельзя.
- Acceptance criterion (D-015): при пропущенной скобке сохранение отклоняется с указанием ошибки, предыдущие сохраненные и примененные настройки не меняются. После исправления синтаксиса допустимо сохранение; проверка совместимости остается отдельным условием применения.
