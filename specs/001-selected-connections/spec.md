## User Scenarios & Testing
Все сценарии ниже PROPOSED; результаты тестов NOT_RUN. Это критерии для обсуждения, не заявление о готовой реализации.

### US-01 — Настроить выбранный внешний узел (приоритет OPEN_QUESTION)
Пользователь задает подключение VLESS, SOCKS, HTTP или WireGuard без настройки OpenWrt со стороны приложения.
- Given выбранный протокол и согласованная версия движка, When пользователь сохраняет допустимые поля, Then значения сохраняют согласованную семантику и преобразуются в ожидаемую конфигурацию.
- Given невыбранный транспорт или неизвестная опция, When она приходит из ввода/импорта, Then приложение не заменяет ее молча другим режимом; конкретная политика отклонения/сохранения требует решения.
- Независимая проверка: синтетические конфигурации и сравнение нормализованных полей с референсом; без реальных секретов.

### US-02 — Понять ошибку до применения (приоритет OPEN_QUESTION)
- Given REALITY+WebSocket либо REALITY+HTTPUpgrade и исследованная версия Xray, When конфигурация проверяется, Then несовместимость выявляется, а не показывается успешное подключение.
- Given недопустимый порт, ID, reserved либо JSON, When выполняется проверка, Then ошибка указывает поле и причину. Ужесточение относительно PassWall обсуждается отдельно.
- Given проверка не запускалась, Then статус NOT_RUN, а не PASS.

### US-03 — Управлять сложными настройками понятно (приоритет OPEN_QUESTION)
- Given выбранный режим, When пользователь редактирует настройки, Then зависимости объяснены и отличены от ограничений движка.
- Given сокращение движения включено, Then переходы не требуют анимации для понимания состояния.
- Given сохраненные и примененные настройки различаются, Then интерфейс не выдает сохранение за успешное применение. Этот UX-процесс пока PROPOSED.

## Requirements
### CONFIRMED
- FR-001: приложение самостоятельно работает на Ubuntu и не зависит от OpenWrt API/LuCI/SSH.
- FR-002: выбранные подключения — VLESS, SOCKS, HTTP-прокси, WireGuard. Локальные inbound-сервисы и системный WireGuard этим не утверждены.
- FR-003: семантика выбранных полей сохраняется максимально точно; отклонения обсуждаются.
- FR-004: Xray-core — основной кандидат; второй движок сейчас не реализуется.
- FR-005: UI следует Apple Design Skill, без копирования LuCI.

### PROPOSED / NEEDS CLARIFICATION
- FR-P01: доменная модель узла отделена от JSON конкретной версии Xray; отсутствующее, пустое и явное default различаются там, где это меняет поведение.
- FR-P02: сохраненная конфигурация проверяется движком до применения; применение/откат и права доступа еще проектируются.
- FR-P03: секреты маскируются в UI и диагностике; формат хранения и выдачи прав не выбран.
- FR-P04: неподдерживаемые сочетания не исправляются автоматически. Решить политику для исторических/импортированных полей.
- FR-P05: каждому принятому полю сопоставлены UI default, нормализация, engine default, validator, зависимости, JSON path и тестовые примеры.

### Key Entities — PROPOSED
Connection: выбранный протокол, общие метаданные, адрес/порт, учетные данные, параметры транспорта/защиты, дополнительные параметры.
EngineCapabilityProfile: версия движка и подтвержденные допустимые комбинации.
ValidationReport: ошибки, предупреждения, NOT_RUN/PASS/FAIL, версия и доказательства выполнения.
Ни SQL-схема, ни язык реализации этим не выбраны.

## Edge Cases
- Поле скрыто, но значение осталось после импорта или переключения режима.
- flow задан, но TLS выключен и encryption=none; PassWall его не передает.
- Пароль без имени пользователя HTTP/SOCKS: исследованный Xray не создает учетную запись.
- Отсутствующий/пустой путь и domain_strategy; Lua трактует их по-разному.
- XHTTP Extra содержит весь объект либо только extra, пользовательский User-Agent уже присутствует.
- FinalMask заменяет автоматически сформированные настройки, а не объединяет их.
- WireGuard endpoint IPv6, reserved 0/3/иная длина, отрицательные/нечисловые keepAlive и MTU.
- DNS адреса узла требует DNS-запроса через еще не работающий узел; bootstrap-петля.
- Неверный gRPC timeout; устаревший импорт transport=quic; REALITY+недопустимый transport.
- Переключение/удаление узла, на который ссылается цепочка: политика не определена.

- SC-005: нет незаявленной OpenWrt-зависимости; UI и конфигурация не теряют выбранные расширенные поля.

## Clarifications
- CONFIRMED D-009: сохранить все шесть транспортов VLESS: RAW (TCP), WebSocket, gRPC, HTTPUpgrade, XHTTP, mKCP. Вопрос о наборе транспортов закрыт. Security/flow и дополнительные возможности не утверждены этим выбором. Ранее перечисленный вопрос о выборе транспортов считать уточненным этой записью.
- CONFIRMED D-010: в первой версии VLESS допускается только с TLS или REALITY. Режим без них запрещен; это явное согласованное отклонение от PassWall. Нельзя автоматически включать незащищенный режим ради поддержки транспорта. Все шесть транспортов остаются целью, их совместимость с защитой проверяется отдельно; конфликт выносится на согласование.
- Acceptance criterion (следствие D-010): конфигурация VLESS без TLS/REALITY не должна считаться допустимой для применения. UI-default и обработка импортированного узла требуют уточнения; автоматическое добавление TLS не разрешено.
- CONFIRMED D-011: поддержать все три значения flow: пустое, xtls-rprx-vision, xtls-rprx-vision-udp443; без автоматической подмены. Пустой flow не означает отключение TLS/REALITY.
- Acceptance criterion (D-011): все три значения сохраняются без потери; генерация учитывает согласованные ограничения engine. Для обычного Vision и Vision-udp443 проверяется различие обработки UDP/443, не обещается доступность UDP вне движка.
- CONFIRMED D-012: несовместимые настройки разрешено сохранять как невалидный черновик с понятной ошибкой, но запрещено применять; без автоматической подмены транспорта/flow/security. Это уточняет FR-P04 и US-02.
- Acceptance criterion (D-012): при сохранении REALITY+WebSocket/HTTPUpgrade для отвергающей сочетание версии Xray узел остается доступным для исправления, помечен невалидным, причина видна, применение блокируется. Значения не исправляются молча. До проверки нельзя утверждать валидность. Жизненный цикл уже примененной конфигурации пока OPEN_QUESTION.
- CONFIRMED D-013: «Сохранить» и «Применить» — отдельные действия. Сохранение не влияет на работающую конфигурацию; изменение работы требует явного применения проверенного состояния. Это уточняет US-03 и FR-P02 в части разделения действий, но не утверждает механизм отката.
- Acceptance criterion (D-013): изменение и сохранение валидного либо невалидного узла не изменяет активную конфигурацию и не инициирует ее перезапуск. Применение возможно только отдельным действием после проверки; UI различает сохраненное и примененное состояние. Гарантии сохранения соединений при самом применении не определены.
- CONFIRMED D-014: сохранить для VLESS редакторы XHTTP Extra и FinalMask. Проверять JSON и совместимость движка, объяснять назначение; FinalMask заменяет автоматически сформированный объект целиком, не выполняет merge. Решение не распространяется автоматически на WireGuard и другие протоколы.
- Acceptance criterion (D-014): валидный XHTTP Extra нормализуется согласно описанному референсу; собственный FinalMask заменяет автоматически собранный, а не смешивается с ним. Ошибка JSON или несовместимость исключает применение. Синтаксически валидный JSON сам по себе не означает совместимость с Xray. Разрешение сохранять синтаксически невалидный JSON как текстовый черновик еще требует уточнения.
- CONFIRMED D-015: XHTTP Extra/FinalMask сохраняются только при синтаксически корректном JSON. Ошибка синтаксиса блокирует сохранение; текст остается в редакторе для исправления, но его долговременная сохранность не гарантируется. Это исключение к широкому прочтению D-012: корректный JSON с несовместимой семантикой можно сохранить невалидным черновиком, применять нельзя.
- Acceptance criterion (D-015): при пропущенной скобке сохранение отклоняется с указанием ошибки, предыдущие сохраненные и примененные настройки не меняются. После исправления синтаксиса допустимо сохранение; проверка совместимости остается отдельным условием применения.
- CONFIRMED D-016: сохранять значения неактивных настроек для возврата, исключать их из конфигурации движка. Свернутый раздел UI не означает неактивность: использовать зависимости режима. Это уточняет вопрос о скрытых полях и FR-P01.
- Acceptance criterion (D-016): после смены XHTTP на RAW и сохранения XHTTP Extra остается в настройках, но отсутствует в генерируемом outbound RAW; возврат к XHTTP восстанавливает значение и снова проверяет применимость. При отключении пользовательского FinalMask сохраненный JSON не заменяет автоматически формируемый объект. Невалидный синтаксис JSON по-прежнему блокирует сохранение; редактирование не изменяет активную конфигурацию до явного применения.
- CONFIRMED D-017: для VLESS сохранить ALPN, uTLS/fingerprint, TLS chain SHA-256 pin, проверяемое имя сертификата, PEM-сертификат проверки, cipher suites, ECH и REALITY ML-DSA-65. Применять зависимости и пояснения, проверять совместимость версии Xray/сервера, не включать дополнительные возможности автоматически. Отключение проверки сертификатов этим не разрешено.
- Acceptance criterion (D-017): каждое из перечисленных полей сохраняется и отображается в соответствующем режиме; активное значение преобразуется согласно SETTINGS_REFERENCE.md, неактивное сохраняется без передачи движку (D-016). Несовместимая активная комбинация блокирует применение с объяснением, а не исправляется молча. Поддержка сертификатов, ECH и ML-DSA-65 требует отдельных положительных/отрицательных проверок целевого движка; результаты пока NOT_RUN.
- CONFIRMED D-018: сохранить для VLESS переключатель Mux, mux_concurrency и xudp_concurrency с UI defaults −1 и 8 соответственно. Не включать автоматически; не обещать ускорение. Семантику специальных значений подтвердить по целевой версии Xray.
- Acceptance criterion (D-018): выбранные значения сохраняются без автоматической подмены; при активном допустимом Mux преобразуются в mux.concurrency и mux.xudpConcurrency. При выключенном Mux concurrency остаются сохраненными, но не передаются как активные настройки; mux.enabled=false допустим как явное отключение. Несовместимость transport/flow/Mux блокирует применение с объяснением, не меняя текущую конфигурацию.
- CONFIRMED D-019: сохранить индивидуальное разрешение доменного имени VLESS-узла через Auto/TCP/UDP/DoH и соответствующие поля DNS-сервера. Общая DNS-политика этим не утверждается. Источник Auto, DNS defaults, маршруты запросов и bootstrap требуют отдельного согласования/исследования.
- Acceptance criterion (D-019): выбранный режим и DNS-параметры сохраняются, активные параметры участвуют в разрешении имени узла, не подменяя незаявленно DNS пользовательских назначений. Неактивные значения подчиняются D-016. Для доменных DNS endpoint необходима проверка bootstrap и отсутствия петель; тесты NOT_RUN, конкретная архитектура еще не выбрана.
- CONFIRMED D-020: сохранить все пять стратегий адресов VLESS-узла и Happy Eyeballs. Переключатель не включается автоматически. При Happy Eyeballs стратегия неактивна, сохраняется для возврата и исключается как активная пользовательская настройка согласно D-016. Эффективное поведение движка требует проверки целевого релиза.
- Acceptance criterion (D-020): переключение Happy Eyeballs не стирает выбранную стратегию; выключение восстанавливает ее доступность. В активном ручном режиме значения соответствуют Auto/UseIPv4v6/UseIPv6v4/UseIPv4/UseIPv6. Auto не заменяется произвольным значением без утвержденного контракта; при включенном Happy Eyeballs конфигурация не содержит конфликтующего неактивного пользовательского выбора. Сетевые тесты двух стеков остаются NOT_RUN.
- CONFIRMED D-021: сохранить VLESS tcp_fast_open и tcpMptcp, default выключено, с пояснением ограничений ОС/сервера/транспорта. Автоматическое изменение настроек ядра ради этих опций не разрешено.
- Acceptance criterion (D-021): сохранение флагов не изменяет системные параметры или активную конфигурацию; при явном применении допустимого сочетания параметры преобразуются в sockopt.tcpFastOpen/tcpMptcp. Не утверждать эффективность для UDP-транспортов и неподдерживаемого окружения. Поведение при недоступной возможности (ошибка/предупреждение) требует отдельного технического контракта.
- CONFIRMED D-022: сохранить все альтернативные режимы chain_proxy VLESS и связанные поля preproxy_node/to_node/outbound_iface. Один дополнительный слой по референсу; не включать режимы одновременно. Проверять совместимость и ссылки, исключать циклы перед применением. Системная настройка интерфейса и роутера не входит в выбор.
- Acceptance criterion (D-022): предварительный и конечный узлы дают различный, соответствующий референсу порядок цепочки; выбор интерфейса ограничивает исходящий интерфейс там, где поддерживается движком. Отсутствующая ссылка, цикл или несовместимость не допускают применения. Смена режима сохраняет неактивные значения без передачи движку (D-016). Runtime-недоступность и политика удаления зависимостей пока OPEN_QUESTION; прямой fallback не утвержден.
- CONFIRMED D-023: блокировать удаление узла, используемого другими сохраненными узлами или активной конфигурацией, с показом зависимостей. Для активных ссылок требуется отдельное применение конфигурации без ссылки. Каскадное удаление и автоматический прямой fallback не разрешены.
- Acceptance criterion (D-023): попытка удалить используемый узел не меняет сохраненные/активные данные и показывает места использования. Удаление разрешается после устранения всех сохраненных и активных зависимостей. Сохранение измененного черновика без применения не снимает блокировку активной ссылки. Обновление подписок этим правилом отдельно не спроектировано.
- CONFIRMED D-024: в первой версии нужны ручное добавление, импорт и подписки для выбранных подключений. Конкретные форматы и операции обновления еще OPEN_QUESTION; новые протоколы и экспорт не утверждены этим выбором.
- Acceptance criterion (D-024): все три способа используют согласованные проверки и не обходят запрет применения невалидных настроек, отдельное явное применение и защиту зависимостей. Реальные URL подписок и учетные данные не попадают в публичные примеры/логи. Подробные сценарии импорта и обновления будут добавлены после согласования форматов и политики.
- CONFIRMED D-025: после загрузки обновления подписки автоматически обновлять сохраненные черновики без предварительного подтверждения diff, показывая результат и конфликты. Активная конфигурация остается неизменной до явного применения. Расписание и автоматический запуск загрузки этим не утверждены.
- Acceptance criterion (D-025): успешное обновление меняет только сохраненное состояние, показывает добавления/изменения/конфликты и не инициирует применение/перезапуск. Узел с сохраненными или активными зависимостями не удаляется автоматически. Невалидные данные не обходят D-012/D-015; политика частичного успеха, ручных правок и сопоставления узлов требует уточнения.
- CONFIRMED D-026: обновление заменяет подписочные параметры узла значениями источника, даже если они редактировались вручную. UI предупреждает о потере таких правок. Не создавать слой ручных overrides. Служебная идентичность и ссылки не являются произвольно заменяемыми параметрами подписки; mapping еще уточняется.
- Acceptance criterion (D-026): после корректного сопоставления узла новое значение подписочного поля заменяет ручное сохраненное значение; предупреждение о таком поведении доступно до редактирования. Обновление не меняет активную конфигурацию и не обходит проверку применимости/защиту зависимостей. Политика отсутствующих полей требует отдельного решения.
- CONFIRMED D-027: исчезнувшие из успешно загруженной и разобранной подписки узлы автоматически удаляются только при отсутствии сохраненных и активных зависимостей. Используемые остаются с отметкой исчезновения и указанием зависимостей. Ошибка загрузки/разбора не является исчезновением.
- Acceptance criterion (D-027): при обновлении с отсутствующим ранее известным узлом без зависимостей он удаляется из сохраненного списка; аналогичный узел с сохраненной или активной ссылкой остается и помечается. Работающий snapshot не изменяется. Пустой/частично разобранный ответ и фильтрация не разрешают массовое удаление без отдельно согласованной политики.
- CONFIRMED D-028: любая ошибка разбора записи отклоняет обновление подписки целиком. Никаких частичных изменений сохраненных узлов и никаких удалений; активная конфигурация также неизменна. Сообщение об ошибке не раскрывает секреты.
- Acceptance criterion (D-028): для подписки с 18 корректными и 2 поврежденными записями набор и параметры сохраненных узлов до/после совпадают, даже если корректные записи содержат новые значения; UI сообщает отклонение и ошибки разбора. Корректно разобранный несовместимый с Xray узел обрабатывается по D-012, а не считается ошибкой разбора. Неизвестный протокол и пустой список пока OPEN_QUESTION.
- CONFIRMED D-029: корректный исходный список подписки с нулем узлов всегда отклоняется с предупреждением; предыдущие сохраненные узлы и активная конфигурация остаются неизменными. Очистка — вручную, с проверкой зависимостей.
- Acceptance criterion (D-029): обновление непустой сохраненной подписки корректным пустым списком не удаляет и не помечает исчезнувшими прежние узлы, показывает отклонение. При первом добавлении такой список также не считается успешным обновлением. Нулевой результат после фильтров или исключения неподдерживаемых протоколов требует отдельной политики.
- CONFIRMED D-030: корректно распознанные неподдерживаемые протоколы пропускаются с отчетом; поддерживаемые обновляются. Ноль поддерживаемых узлов после этого отбора отклоняет обновление без изменений. Неизвестный либо поврежденный формат не пропускается под видом корректной записи; применяется D-028.
- Acceptance criterion (D-030): смешанная подписка с корректными поддерживаемыми и распознанными неподдерживаемыми записями обновляет поддерживаемые и сообщает пропуски без секретов; подписка только с неподдерживаемыми не меняет сохраненные узлы и не запускает удаления. Ошибка разбора поддерживаемой записи по-прежнему отклоняет всё обновление. Активное состояние не меняется.
- CONFIRMED D-031: сохранить все режимы фильтрации подписок PassWall: выключено, discard, keep, discard с приоритетом keep, keep с приоритетом discard, наследование глобальной настройки; соответствующие списки ключевых слов. Семантику сопоставления и defaults подтвердить исходниками.
- Acceptance criterion (D-031): режим и списки сохраняются; для каждого режима должны быть примеры совпадения только keep, только discard, обоих и ни одного. Проверяется наследование глобального режима. Ожидаемые результаты сопоставления, нулевой выборки и удаления после фильтра задаются после исследования/согласования, не предполагаются.
- CONFIRMED D-032: нулевой результат фильтрации подписки отклоняет обновление; сохраненные узлы и активная конфигурация остаются неизменными. UI объясняет, что записи исключены фильтрами.
- Acceptance criterion (D-032): непустая корректная подписка, все узлы которой исключены фильтром, не приводит ни к удалению, ни к изменению/пометке исчезновения прежних узлов. Пустой keep в соответствующем режиме проверяется отдельным отрицательным сценарием. Результат показывается как отклоненный, а не успешное пустое обновление.
- CONFIRMED D-033: ручной запуск, один раз после загрузки ОС, ежедневно, выбранный день недели и интервал 1–24 часа; автоматические режимы выключены по умолчанию. Не зависеть от OpenWrt. Подробная семантика времени и повторов пока OPEN_QUESTION.
- Acceptance criterion (D-033): без явного включения автоматического режима подписки не загружаются по расписанию/после загрузки ОС. Каждый разрешенный триггер использует одинаковые проверки обновления и не применяет конфигурацию к сети автоматически. Повторный запуск службы в пределах одной загрузки ОС не должен сам по себе считаться новой загрузкой ОС; механизм учета еще проектируется.
- CONFIRMED D-034: для каждой подписки доступны способы загрузки Auto/Direct/Proxy. Семантика Auto, выбор прокси и политика отказа еще OPEN_QUESTION. Выбор не разрешает скрытый fallback на прямое соединение.
- Acceptance criterion (D-034): способ загрузки сохраняется отдельно от настроек импортируемых узлов и общей маршрутизации. UI не выдает Auto за гарантированно проксированный путь. Для каждого режима потребуется проверка фактического маршрута запросов после утверждения семантики; сетевые тесты NOT_RUN.
- CONFIRMED D-035: загрузка подписки в режиме Proxy при недоступном прокси завершается ошибкой без перехода на Direct. Сохраненные узлы и активная конфигурация остаются неизменными; выбранный режим не меняется автоматически.
- Acceptance criterion (D-035): при недоступном прокси ручное и запланированное обновление сообщают ошибку, не отправляют прямой запрос к URL подписки и не изменяют список узлов. Проверка DNS/bootstrap выполняется отдельно: запрет прямого HTTP-запроса сам по себе не доказывает отсутствие DNS-утечки. Auto и отказ пользовательского трафика этим не определены.
- CONFIRMED D-036: проверять сертификат и имя HTTPS-источника по умолчанию; разрешить отдельное опасное исключение для конкретной подписки с предупреждением. Исключение включается только явно, не автоматически после ошибки и не из содержимого подписки. Оно не меняет TLS-проверки узлов/других подписок.
- Acceptance criterion (D-036): неверный сертификат либо имя сервера без исключения блокирует обновление и не изменяет узлы; повтор не отключает проверку автоматически. После явного включения исключения UI показывает опасный режим, применяемый только к соответствующей подписке. Отключение исключения восстанавливает проверку при следующей загрузке. Redirect и HTTP-policy остаются OPEN_QUESTION.
- CONFIRMED D-037: обычные HTTP-подписки разрешены с предупреждением, без дополнительного разрешения. Предупреждение сообщает отсутствие шифрования и риск перехвата/подмены. Режим Proxy сам по себе не убирает этот риск. Настройка не меняет проверку HTTPS и не разрешает автоматически downgrade redirect.
- Acceptance criterion (D-037): HTTP URL можно сохранить и загрузить без отдельного опасного флага; UI явно предупреждает о незащищенном источнике. Все правила разбора, обновления, защиты зависимостей и явного применения сохраняются. Политика HTTPS→HTTP перенаправления остается OPEN_QUESTION.
- CONFIRMED D-038: автоматически следовать HTTPS→HTTP перенаправлению при загрузке подписки, предупреждать о понижении защиты в результате. Предварительного подтверждения не требуется. Это не меняет проверку исходного HTTPS-соединения и не разрешает Proxy→Direct fallback.
- Acceptance criterion (D-038): допустимый HTTPS-ответ с redirect на HTTP может привести к HTTP-запросу автоматически; результат явно отмечает downgrade, в том числе при последующей ошибке обновления. Для Proxy все запросы остаются проксированными либо загрузка завершается ошибкой. Если исходный HTTPS не проходит обязательную проверку сертификата, запрос к redirect-цели не выполняется. Переходы между origin, лимит redirect и передача авторизации еще OPEN_QUESTION.
- CONFIRMED D-039: для подписки доступны свободный ввод User-Agent и готовые варианты. Набор точных строк и default еще OPEN_QUESTION; User-Agent загрузчика отделен от User-Agent транспорта узла.
- Acceptance criterion (D-039): выбранная готовая или пользовательская строка сохраняется для конкретной подписки и используется загрузчиком; не подменяет транспортные параметры узлов. Формат ответа проверяется независимо от выбранного имени клиента. Валидация HTTP-header (включая недопустимые CR/LF) требует технического контракта до реализации.
- CONFIRMED D-040: форматы подписок — текстовые и Base64-списки ссылок, Clash/Mihomo YAML с извлечением только узлов выбранных протоколов. Правила, DNS и группы из YAML автоматически не импортируются. Матрица поддержанных полей/версий и схем URI еще уточняется.
- Acceptance criterion (D-040): эквивалентные поддерживаемые узлы из согласованных форматов приводятся к одинаковой доменной семантике; содержимое rules/dns/proxy-groups не изменяет настройки Raylane. Неподдержанные протоколы и ошибки обрабатываются по D-030/D-028, нулевая выборка — по согласованным правилам. Поддержка формата не означает выполнение YAML tags или автоматическую загрузку внешних provider/include URL.
- CONFIRMED D-041: неизвестные параметры синтаксически корректного импортируемого узла выбранного протокола сохраняются вместе с невалидным черновиком; применение блокируется до явного решения пользователя. Не отбрасывать и не выполнять их молча. Известные исключенные разделы YAML обрабатываются по D-040, а не как неизвестные поля узла.
- Acceptance criterion (D-041): импорт с неизвестным полем выбранного протокола сохраняет поле без потери, показывает причину невалидности и запрещает применение. Значения потенциально секретных полей не появляются в диагностических журналах/публичных артефактах. Ошибки синтаксиса остаются основанием отклонить обновление целиком; неизвестное поле само по себе не является такой ошибкой. Процедура явного разрешения вопроса еще OPEN_QUESTION.
- CONFIRMED D-042: неизвестные импортированные поля не разрешается отбрасывать через интерфейс исправления для обхода блокировки. Ждать поддержки или исправления источника; после этого повторить проверки. «Применить всё равно» не предоставляется.
- Acceptance criterion (D-042): черновик с неизвестными полями остается неприменимым, пока они не поддержаны или не устранены исправлением источника. UI показывает причину и допустимые пути решения, не предлагает проигнорировать/удалить поля ради применения. При обновлении поддержки не происходит автоматического применения к сети; требуется обычная проверка и явное действие пользователя.
- CONFIRMED D-043: внешние SOCKS5 и HTTP-прокси поддерживают подключение без авторизации либо с username/password. SOCKS4/4a и локальные proxy-inbound этим не включены.
- Acceptance criterion (D-043): оба режима доступны и сохраняются; в режиме без авторизации не используются неактивные credentials, в режиме с авторизацией поддерживаемые значения передаются в settings.user/pass. Секреты не выводятся в журналы. Пограничные значения (пустое имя/пароль) проверяются по отдельному согласованному контракту, а не заменяются автоматически.
- CONFIRMED D-044: внешний HTTP-прокси поддерживает обычное подключение и подключение поверх TLS. UI различает защиту канала до прокси и HTTPS сайта назначения. REALITY для HTTP не включен этим решением.

Переключение сохраняет неактивные TLS-поля без их применения (D-016), не изменяет активную конфигурацию до явного применения. Набор TLS-полей и политика проверки сертификата еще уточняются.
